# CRAN Package Architecture Requirements

**Domain:** R Package for CRAN Submission
**Researched:** 2026-01-22
**Confidence:** HIGH

## Executive Summary

CRAN package architecture follows strict conventions defined in "Writing R Extensions" and enforced through automated checks. The structure consists of mandatory files (DESCRIPTION, NAMESPACE) and optional but standard directories (R/, man/, tests/, vignettes/, src/, inst/, data/). All packages must pass `R CMD check --as-cran` without errors or warnings. The architecture emphasizes clear separation between code, documentation, tests, and data, with specific naming conventions and organizational rules for each component.

## Required Package Components

### Absolutely Mandatory

| Component | Purpose | Format |
|-----------|---------|--------|
| DESCRIPTION | Package metadata and dependencies | DCF (Debian Control Format) |
| NAMESPACE | Export/import control | Generated by roxygen2 or manual |

**Critical:** These two files are the minimum required for a valid R package. Without them, the package cannot be built or installed.

### Standard Directories (Optional but Expected)

| Directory | Purpose | Required for CRAN? |
|-----------|---------|-------------------|
| R/ | R source code | Yes (packages need code) |
| man/ | Documentation (.Rd files) | Yes (all exports must be documented) |
| tests/ | Unit tests | Strongly recommended |
| vignettes/ | Long-form documentation | Recommended |
| data/ | Package datasets | If applicable |
| src/ | Compiled code (C/C++/Fortran) | If applicable |
| inst/ | Files to install with package | If needed |

**Note:** Directories should not exist if empty. CRAN checks will note empty directories.

## DESCRIPTION File Requirements

### Mandatory Fields

```r
Package: delarr                    # Package name (letters, numbers, dots only)
Type: Package                       # Usually "Package"
Title: [65 chars max, title case]  # No ending period
Version: 0.1.0                     # Semantic versioning (major.minor.patch)
Authors@R: person(...)             # Author and maintainer specification
Description: [80 chars per line]   # One paragraph, detailed explanation
License: MIT + file LICENSE        # Must be in official license database
```

### Critical DESCRIPTION Requirements

**Authors@R Format:**
```r
Authors@R: c(
    person(given = "Ben",
           family = "Buchsbaum",
           role = c("aut", "cre"),
           email = "ben@example.com",
           comment = c(ORCID = "0000-0000-0000-0000"))  # Optional but recommended
)
```

**Role Codes:**
- `cre`: Creator/maintainer (exactly one required, must be a person not mailing list)
- `aut`: Author with significant contributions (at least one required)
- `ctb`: Contributor (smaller contributions)
- `cph`: Copyright holder (often companies)
- `fnd`: Funder

**Email Requirements:**
- Must be current and unfiltered
- Maintainer email receives all CRAN communications
- Should be durable (not tied to temporary institution)

### Dependency Fields

**Imports** (Required for functionality):
```r
Imports:
    rlang,
    methods
```
- Packages needed at runtime
- Installed automatically with your package
- Must specify minimum version if dependent on specific features: `dplyr (>= 1.0.0)`

**Suggests** (Optional/developmental):
```r
Suggests:
    testthat (>= 3.1.0),
    knitr,
    rmarkdown,
    matrixStats,
    hdf5r
```
- Packages for tests, vignettes, or optional features
- Not installed automatically
- Used conditionally (check with `requireNamespace()`)

**Depends** (Rarely used):
```r
Depends:
    R (>= 4.1)
```
- Primarily for R version requirements
- For packages: attaches them when your package loads (usually wrong choice)
- Prefer Imports for package dependencies

**LinkingTo** (C/C++ headers):
```r
LinkingTo:
    Rcpp,
    RcppArmadillo
```
- Packages providing C/C++ header files
- Required if you include C++ code using their headers

### Important Optional Fields

```r
URL: https://github.com/username/delarr,
    https://username.github.io/delarr/
BugReports: https://github.com/username/delarr/issues
Encoding: UTF-8
LazyData: false                          # Set false if no data/ directory
VignetteBuilder: knitr                   # If vignettes/ exists
Config/testthat/edition: 3               # If using testthat
Roxygen: list(markdown = TRUE)
RoxygenNote: 7.3.2                       # Auto-generated by roxygen2
```

### DESCRIPTION Best Practices

**Title Field:**
- Max ~65 characters
- Title case (capitalize major words)
- No ending period
- Don't start with "A package for..." or repeat package name
- Use single quotes around software/package names: `'tidyverse'`

**Description Field:**
- One paragraph explaining what the package does
- Max 80 characters per line (continuation lines indented 4 spaces)
- Use function names with parentheses: `foo()`
- Cite relevant papers in author-year format: `Smith (2023) <doi:10.1234/example>`
- Explain all acronyms
- Single quotes around non-English terms, package names, software names

**Common Rejection Reasons:**
- Title/Description not informative enough
- Missing copyright holders (use `cph` role)
- Improper citation formats
- Package name repeated in Title
- Non-standard fields without `Config/` prefix

## NAMESPACE File Requirements

### Purpose

Controls which functions are:
- **Exported** (visible to package users)
- **Imported** (from other packages)
- **S3 methods registered** (for generic functions)

### Recommended Approach: Use roxygen2

Modern best practice is to generate NAMESPACE automatically using roxygen2 comments in R source files.

**Current delarr NAMESPACE (good example):**
```r
# Exported functions
export(delarr)
export(d_map)
export(collect)
export(rowMeans2)

# S3 methods
S3method(dim, delarr)
S3method(`[`, delarr)
S3method(print, delarr)
S3method(Ops, delarr)
S3method(rowMeans2, delarr)
```

### Roxygen2 Tags for NAMESPACE

**Export a function:**
```r
#' @export
my_function <- function() { }
```

**Export S3 method:**
```r
#' @export
print.delarr <- function(x, ...) { }
# OR explicitly:
#' @exportS3Method print delarr
```

**Import functions from other packages:**
```r
#' @importFrom rlang .data quo enquo
#' @importFrom stats na.omit
```

**Import entire package namespace (discouraged):**
```r
#' @import magrittr
```

### Critical NAMESPACE Rules

1. **All exported functions must be documented** with .Rd files in man/
2. **All S3 methods should be registered** even if not exported
3. **Use :: for external functions** rather than importing entire namespaces
4. **Never edit NAMESPACE manually** if using roxygen2 (add warning comment)
5. **Import generics before defining methods**: If you define `print.myclass`, import `print` from base

## R/ Directory Structure

### File Organization

**Current delarr structure (good example):**
```
R/
├── delarr-core.R         # Core constructor and class definition
├── delarr-backends.R     # Backend implementations
├── delarr-eval.R         # Evaluation engine
├── delarr-seed.R         # Seed objects
├── delarr-verbs.R        # User-facing functions
├── delarr-writer-hdf5.R  # Specific writer implementation
├── delarr-helpers.R      # Internal helpers
├── generics.R            # Generic function definitions
└── utils.R               # Utility functions
```

### Best Practices

**File Naming:**
- Start with letter or digit
- Use `.R` extension (uppercase recommended)
- Group related functions: `package-topic.R`
- Special files:
  - `package.R` or `package-package.R`: package-level documentation
  - `generics.R`: all generic definitions
  - `utils.R`: utility functions
  - `zzz.R`: `.onLoad()`, `.onAttach()` hooks

**Code Organization:**
1. Source files should primarily contain assignments
2. Avoid side effects (no `library()`, `require()`, `options()`)
3. Collation order controlled by `@include` roxygen tags if needed
4. Objects defined across files must maintain consistent order

**Special .R Files:**

**Package documentation (delarr-package.R):**
```r
#' @keywords internal
"_PACKAGE"

## usethis namespace: start
## usethis namespace: end
NULL
```

**.onLoad() hook (zzz.R):**
```r
.onLoad <- function(libname, pkgname) {
  # Package initialization
  # Set options, register S3 methods, etc.
}

.onAttach <- function(libname, pkgname) {
  # Startup message (use sparingly)
  packageStartupMessage("Welcome to delarr")
}
```

### Code Quality Requirements

**For CRAN:**
- No syntax errors (obviously)
- No warnings in R CMD check
- Use `if (FALSE)` instead of commenting out examples
- Conditional examples for optional dependencies:
  ```r
  #' @examples
  #' if (requireNamespace("ggplot2", quietly = TRUE)) {
  #'   # Example using ggplot2
  #' }
  ```

## man/ Directory (Documentation)

### Purpose

Contains R documentation (.Rd) files generated by roxygen2 from source code comments.

### Requirements

**All exported objects must be documented:**
- Functions: parameters, return value, examples
- Datasets: description, format, source
- Classes: slots, methods, usage
- S3 methods: differences from generic

### Current delarr Structure (29 .Rd files)

```
man/
├── delarr.Rd                 # Main constructor
├── d_map.Rd                  # Verb functions
├── collect.Rd                # Core functions
├── print.delarr.Rd           # S3 methods
├── rowMeans2.Rd              # Generic
├── rowMeans2.delarr.Rd       # S3 method
└── ...                       # All exported objects
```

### Roxygen2 Documentation Template

```r
#' Brief title (one line)
#'
#' Detailed description paragraph. Can span multiple lines and
#' include markdown formatting.
#'
#' @param x Description of parameter x
#' @param y Description of parameter y (default: NULL)
#' @param ... Additional arguments passed to methods
#'
#' @return Description of return value. Be specific about type/structure.
#'
#' @details
#' Additional details about function behavior, algorithms, special cases.
#'
#' @examples
#' # Simple example
#' result <- my_function(1:10)
#'
#' # More complex example
#' if (requireNamespace("dplyr", quietly = TRUE)) {
#'   library(dplyr)
#'   result <- my_function(mtcars$mpg)
#' }
#'
#' @seealso [related_function()], [other_function()]
#'
#' @export
my_function <- function(x, y = NULL, ...) {
  # Implementation
}
```

### Critical Documentation Requirements

**Mandatory for CRAN:**
- `@param` for every parameter
- `@return` describing what the function returns
- `@examples` that run without error
- Valid syntax in all code examples

**Examples Rules:**
- Must run successfully in `R CMD check`
- Use `\dontrun{}` sparingly (CRAN discourages it)
- For time-consuming examples: `\donttest{}`
- For examples requiring unavailable resources: conditional execution
- Cannot write to user directories (use `tempdir()`)

**S3 Method Documentation:**
```r
#' @rdname delarr     # Document with main function
#' @export
print.delarr <- function(x, ...) { }
```

### Documentation Best Practices

1. **One object per file** (generally) or group related methods with `@rdname`
2. **Use markdown**: enabled with `Roxygen: list(markdown = TRUE)` in DESCRIPTION
3. **Link to related functions**: `[other_function()]`
4. **Include references**: `@references Author (2023). Title. Journal. doi:xxx`
5. **Real-world examples**: Show typical use cases, not just syntax

## tests/ Directory Structure

### Standard testthat Setup

**Required structure:**
```
tests/
├── testthat.R              # Entry point (DO NOT EDIT)
└── testthat/
    ├── test-backend.R      # Test files (start with "test-")
    ├── test-verbs.R
    ├── test-eval.R
    ├── helper.R            # Helper functions (optional)
    ├── setup.R             # Setup code (optional)
    └── _snaps/             # Snapshot tests (if used)
```

### tests/testthat.R Template

```r
# This file is part of the standard setup for testthat.
# It is recommended that you do not modify it.
#
# Where should you do additional test configuration?
# Learn more about the roles of various files in:
# * https://r-pkgs.org/tests.html
# * https://testthat.r-lib.org/reference/test_package.html#special-files

library(testthat)
library(delarr)

test_check("delarr")
```

### Test File Organization

**File naming:**
- Must start with `test-`: `test-backend.R`, `test-verbs.R`
- Group related tests by functionality
- One file per major feature/component

**Test structure:**
```r
test_that("descriptive test name", {
  # Setup
  x <- delarr(matrix(1:10, 2, 5))

  # Action
  result <- d_map(x, function(z) z * 2)

  # Assertion
  expect_equal(dim(result), c(2, 5))
  expect_true(inherits(result, "delarr"))
})
```

### CRAN Testing Requirements

**DESCRIPTION dependencies:**
```r
Suggests:
    testthat (>= 3.1.0)
Config/testthat/edition: 3
```

**Test execution constraints:**
- Tests must complete quickly (seconds, not minutes)
- Long-running tests: wrap in `skip_on_cran()`
- Tests requiring external resources: skip conditionally
- No writes to user directories (use `tempdir()`)
- No internet access assumed

**Conditional testing:**
```r
test_that("HDF5 backend works", {
  skip_if_not_installed("hdf5r")
  skip_on_cran()  # If slow or requires special setup

  # Test code
})
```

### Special Files

**helper.R** (loaded with `devtools::load_all()`):
```r
# Helper functions available to all tests
make_test_matrix <- function(nrow = 10, ncol = 10) {
  matrix(rnorm(nrow * ncol), nrow, ncol)
}
```

**setup.R** (run before tests, not loaded by devtools):
```r
# One-time setup for all tests
# Set options, create shared resources, etc.
options(delarr.test_mode = TRUE)
```

### Purpose

Long-form documentation explaining package concepts, workflows, and use cases.

### Basic Structure

```
vignettes/
├── introduction.Rmd        # Getting started
```

### DESCRIPTION Requirements

```r
Suggests:
    knitr,
    rmarkdown
VignetteBuilder: knitr
```

### CRAN Vignette Requirements

**Building:**
- Vignettes must build successfully without errors
- CRAN rebuilds vignettes regularly for quality control
- Build time should be reasonable (minutes, not hours)

**Dependencies:**
- All packages used must be in Imports or Suggests
- External data must be small or downloaded conditionally
- No internet access assumed

**Size constraints:**
- Vignettes with many graphics can become large
- Keep total size reasonable (< 5MB for vignette output)
- Use compression for images

**Best practices:**
```r
# Conditional code for optional dependencies
if (requireNamespace("ggplot2", quietly = TRUE)) {
  library(ggplot2)
  # Plotting code
} else {
  message("ggplot2 not available, skipping visualization")
}
```

For vignettes requiring:
- Long computation time
- Unavailable external resources
- Special hardware

**Solution:** Pre-compute and include HTML:

## Optional Directories

### src/ (Compiled Code)

**Purpose:** C, C++, Fortran, Objective-C/C++ source code

**Supported extensions:**
- C: `.c`
- C++: `.cc`, `.cpp`, `.cxx`
- Fortran: `.f`, `.f90`, `.f95`
- Objective-C/C++: `.m`, `.mm`

**Build control:**
- `Makevars`: Unix/Linux/macOS configuration
- `Makevars.win`: Windows configuration
- `configure`: Pre-build configuration script

**CRAN requirements:**
- Must compile on major platforms (Linux, macOS, Windows)
- Cannot terminate R process
- Must handle memory correctly (no leaks)
- Use portable code (avoid platform-specific features)

**delarr:** Currently has empty `src/`, can be removed if unused.

### inst/ (Installation Files)

**Purpose:** Files copied recursively to installation directory

**Common uses:**
```
inst/
├── CITATION            # How to cite the package
├── extdata/           # External data files
├── scripts/           # Example scripts
├── templates/         # File templates
└── rstudio/           # RStudio addins
```

**Access installed files:**
```r
system.file("extdata", "myfile.csv", package = "delarr")
```

**Restrictions:**
- Avoid R-reserved names: R, data, demo, exec, libs, man, help, html, Meta
- Use `.Rinstignore` to exclude files from installation

### data/ (Package Data)

**Purpose:** Datasets accessible via `data()`

**Supported formats:**
- `.rda`/`.RData`: Binary R objects (preferred)
- `.R`: R code creating objects
- `.txt`/`.csv`/`.tab`: Plain text tables

**Best practices:**
- Keep datasets small (< 1MB each, < 5MB total)
- Large data: create separate data package
- Document in `R/data.R`:
  ```r
  #' Dataset name
  #'
  #' Description of dataset.
  #'
  #' @format A data frame with X rows and Y variables:
  #' \describe{
  #'   \item{variable1}{description}
  #'   \item{variable2}{description}
  #' }
  #' @source \url{http://example.com}
  "dataset_name"
  ```

**DESCRIPTION field:**
```r
LazyData: true  # Load on demand (recommended)
```

## File Naming Conventions

### General Rules

**CRAN requirements:**
- Start with ASCII letter or digit
- No control characters
- Forbidden: `" * : / < > ? \ |`
- Avoid: `'`, space, shell metacharacters
- Case-sensitive filesystems: avoid case-only differences

**Platform portability:**
- Windows reserved names: `con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`
- Path length: Keep under 100 bytes for maximum compatibility
- Use forward slashes in R code (even on Windows)

### Directory-Specific Rules

| Directory | Pattern | Example |
|-----------|---------|---------|
| R/ | `[name].R` | `delarr-core.R` |
| man/ | `[name].Rd` | `delarr.Rd` |
| tests/testthat/ | `test-[name].R` | `test-backend.R` |
| vignettes/ | `[name].Rmd` | `introduction.Rmd` |
| data/ | `[name].rda` | `example_data.rda` |

## Version Control and CRAN Files

### Version Numbering

**Semantic versioning:** `major.minor.patch` or `major.minor.patch.dev`

**CRAN submissions:**
- Development: `0.0.0.9000` (before first release)
- First release: `0.1.0` or `1.0.0`
- Patch: `1.0.1` (bug fixes only)
- Minor: `1.1.0` (new features, backward compatible)
- Major: `2.0.0` (breaking changes)

**Version increments:**
- Every CRAN submission must increase version number
- Use `usethis::use_dev_version()` after CRAN acceptance

### NEWS.md

**Purpose:** Document changes for users

**Format:**
```markdown
# delarr 0.1.0

## New features

* Added `d_map()` function for element-wise operations
* New HDF5 backend via `delarr_hdf5()`

## Bug fixes

* Fixed dimension handling in `collect()` (#42)
* Corrected memory leak in backend cleanup (#38)

## Breaking changes

* Renamed `delarr_create()` to `delarr()` for simplicity

# delarr 0.0.0.9000

* Initial development version
```

**Best practices:**
- Top version first (newest at top)
- Level 1 heading for each version
- Level 2 headings for categories
- Bullet points for individual changes
- Link to GitHub issues: `(#42)`
- Keep all history (never delete old entries)

### cran-comments.md

**Purpose:** Communication with CRAN reviewers

**Template:**
```markdown
## Resubmission

This is a resubmission. In this version I have:

* Fixed the invalid URL in the Description field
* Added `\value` sections to all exported function documentation

## R CMD check results

0 errors | 0 warnings | 0 notes

## Reverse dependencies

There are currently no reverse dependencies for this package.
```

**Include:**
- Resubmission changes (if applicable)
- R CMD check results from multiple platforms
- Explanation of any unavoidable NOTEs
- Reverse dependency check results

**Test platforms:**
```markdown
## Test environments

* local: macOS 14.1, R 4.4.0
* win-builder: R-devel and R-release
* GitHub Actions: windows-latest, macOS-latest, ubuntu-latest (R-release, R-devel)
```

## R CMD check Requirements

### Zero Tolerance

**For CRAN submission:**
- 0 ERRORS (required)
- 0 WARNINGS (required)
- 0 NOTEs (preferred, or explained)

### Running Checks

**Local check:**
```r
devtools::check()
# OR
rcmdcheck::rcmdcheck()
```

**CRAN-like check:**
```r
devtools::check(remote = TRUE, manual = TRUE, cran = TRUE)
```

**Windows check:**
```r
devtools::check_win_devel()  # R-devel
devtools::check_win_release()  # R-release
```

**Multi-platform check:**
```r
# Using GitHub Actions (recommended)
usethis::use_github_action("check-standard")

# Using R-hub (alternative)
rhub::check_for_cran()
```

### Common Check Issues

**DESCRIPTION problems:**
- Invalid maintainer email format
- Missing or malformed license
- Imports not used, or used but not imported
- Title/Description not informative enough

**NAMESPACE problems:**
- Exported objects without documentation
- Imported packages not in DESCRIPTION
- S3 methods not properly registered

**Documentation problems:**
- Missing `@param` or `@return` tags
- Examples that fail or write to user directories
- Code-documentation mismatches
- Invalid cross-references

**Code problems:**
- Syntax errors
- Undefined global variables (use `.data` from rlang)
- Non-portable file paths
- Platform-specific code without checks

### Notes That Are Acceptable

**New submissions:**
```
New submission
```

**Maintainer email change:**
```
Maintainer: 'New Name <new@email.com>'
Old maintainer: 'Old Name <old@email.com>'
```

**Large package (if justified):**
```
checking installed package size ... NOTE
  installed size is XX Mb
```

**Explain in cran-comments.md** why these notes are unavoidable.

## Submission Checklist

### Pre-Submission

- [ ] Version number updated
- [ ] NEWS.md updated with changes
- [ ] All dependencies in DESCRIPTION (Imports/Suggests)
- [ ] README.md current and accurate
- [ ] `devtools::check()` passes with 0 errors, 0 warnings, 0 notes
- [ ] `devtools::check_win_devel()` passes
- [ ] Documentation complete for all exports
- [ ] Examples run successfully
- [ ] Tests pass (including on CRAN)
- [ ] Vignettes build successfully
- [ ] `urlchecker::url_check()` passes
- [ ] `spelling::spell_check_package()` passes
- [ ] Review cran-comments.md

### Submission Process

**Method:** Use web form at https://cran.r-project.org/submit.html

**Using R:**
```r
devtools::submit_cran()
```

**Steps:**
1. Upload package bundle (`.tar.gz` from `R CMD build`)
2. Fill in maintainer details
3. Add optional comments
4. Accept terms
5. Receive confirmation email
6. Click confirmation link
7. Monitor https://cran.r-project.org/incoming/

**Timeline:**
- Initial checks: Minutes to hours
- Human review: Days to weeks (first submission slower)
- Response: Via email to maintainer

### After Submission

**If accepted:**
```r
# Create GitHub release
usethis::use_github_release()

# Bump to development version
usethis::use_dev_version()

# Monitor CRAN check results
# https://cran.r-project.org/web/checks/check_results_[package].html
```

**If rejected:**
1. Read feedback carefully
2. Fix identified issues
3. Increment version (patch bump)
4. Update cran-comments.md with fixes
5. Resubmit after all fixes complete

**Maintenance:**
- Respond to CRAN emails promptly (typically 2 weeks deadline)
- Update for R-devel changes before major R releases
- Limit resubmissions to every 1-2 months (established packages)
- Notify reverse dependency maintainers 2+ weeks before breaking changes

## Architecture Patterns

### Do This

**Modular file organization:**
```
R/
├── [package]-core.R      # Core functionality
├── [package]-verbs.R     # User-facing API
├── [package]-backend.R   # Implementation details
├── generics.R            # S3 generics
└── utils.R               # Internal helpers
```

**Clean exports:**
- Export high-level user functions
- Keep implementation details internal
- Use `@keywords internal` for truly internal docs

**Dependency hygiene:**
- Minimize dependencies
- Use Suggests for optional features
- Import specific functions, not entire packages

**Test organization:**
```
tests/testthat/
├── test-core.R           # Core functionality
├── test-backend.R        # Backend implementations
├── test-integration.R    # Integration tests
└── helper.R              # Test utilities
```

### Avoid This

**Anti-patterns:**
- Single huge R file with everything
- Exporting internal implementation functions
- Using `:::` to access internals from other packages
- Writing to user home directory
- Modifying global options without restoration
- Long-running examples (> 5 seconds)
- Tests that require internet or external resources
- Large binary files in the package
- Non-portable file paths (e.g., Windows-specific)

**CRAN policy violations:**
- Compiled code that can crash R
- Telemetry or phone-home without consent
- Modifying loaded packages
- Writing to user directories outside `tools::R_user_dir()`
- Disabling compiler warnings
- Bypassing SSL/TLS verification

## Platform Compatibility

### Required Platforms

CRAN expects packages to work on:
- Linux (Debian/Ubuntu, Fedora/RHEL)
- macOS (Intel and ARM/M1)
- Windows

Minimum: Two major platforms. Windows-only packages need strong justification.

### Platform-Specific Code

**Conditional execution:**
```r
if (.Platform$OS.type == "windows") {
  # Windows-specific code
} else {
  # Unix-like code
}

if (Sys.info()["sysname"] == "Darwin") {
  # macOS-specific code
}
```

**Platform-specific files:**
- `Makevars` (Unix/Linux/macOS)
- `Makevars.win` (Windows)
- `configure` (Unix-like)
- `configure.win` (Windows)

### Testing Across Platforms

**Continuous Integration:**
```yaml
# GitHub Actions matrix
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macOS-latest]
    r: [release, devel]
```

**Manual testing:**
- `devtools::check_win_devel()` - Windows R-devel
- `devtools::check_win_release()` - Windows R-release
- `devtools::check_mac_release()` - macOS (via MacBuilder)
